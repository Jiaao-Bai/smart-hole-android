# 产品方向与功能基线

## 唯一目标

Smart Hole 要做的是一款真正好用的手机 Agent。

它不是桌面 DeepSeek Harness 的 Android 平替，也不以复刻某个桌面产品为目标。
评价它是否成功，最终看的是一个人能否在手机上自然、可靠、高频地把事情交给它，
而不是功能清单与桌面界面是否一一对应。

## 当前实现条件

这个目标目前先在 Android 上实现，因为 Agent 若要完整操作本地文件、应用和系统，
现阶段需要 Root。Root 是当前技术条件和执行边界，不是产品定位；未来若其他平台
能够提供足够的本地能力，产品目标本身不需要改变。

## DSH 是最低能力基线

Smart Hole 以官方 DeepSeek Harness 作为 Agent 引擎。DSH 原生提供的通用能力必须
完整可用，否则手机 Agent 从一开始就是残缺的。这些能力包括会话、模型、Shell、
文件、搜索、后台任务、Skill、Todo、Web、提问与审批、Goal、Plan Mode、子 Agent、
工作流、Ralph、Provider 和插件机制。

达到这条基线只表示“底层 Agent 能力完整”，不表示 Smart Hole 已经足够好用。
桌面托盘、窗口和多栏布局也不属于要复制的 DSH 功能；手机端应以自己的方式承担
对应职责。

## 当前基线完成度

| 能力 | 状态 | 当前实现 |
| --- | --- | --- |
| 官方 Agent/Session/模型/工具运行时 | 已具备 | 固定版本的官方 DSH Host 直接运行在 Android/Bionic Node.js 上 |
| 流式对话、历史会话、取消 | 已具备 | 原生 Compose 界面通过官方 RPC 与 WebSocket 连接 Host |
| Shell、文件、搜索、后台任务、Skill、Todo、Web | 部分原生化 | 使用官方 DSH 工具；工具插件的 Presentation 已进入通用原生卡片，管理入口仍不完整 |
| 用户提问与审批 | 已具备 | 官方交互协议与 `/api/respond`，由原生卡片呈现 |
| Goal、Todo、Plan Mode | 部分原生化 | 独立 Feature Module 读取官方 Projection；Goal/Todo 原生展示、Plan 有手机端入口，完整编辑控制仍待完成 |
| 子 Agent | 部分原生化 | 保留 Host 的子会话，按父子关系原生展示运行状态、耗时和 Token，可进入子会话查看完整记录 |
| Fork、工作流、Ralph | Host 已具备 | 官方标准插件已经进入 Android 工具目录，尚缺专用手机交互 |
| 模型与思考强度选择 | 已具备 | 动态读取 `session.models`，通过 `session.selectModel` 设置 |
| DeepSeek 凭据 | 已具备 | 经官方只写凭据接口保存，App 不读取明文 |
| 多 Provider 配置 | 部分具备 | Host 能力存在，原生管理界面尚未完成 |
| 插件安装与管理 | 待完成 | Host 可加载插件，尚无原生管理界面 |
| 文件与图片附件 | 待完成 | 尚无 Android 选择、分享与附件发送入口 |
| 用户可用的 PTY 终端 | 待完成 | Agent 可用 Shell 和后台任务，尚无交互终端界面 |

“已具备”要求复用官方 Host 语义，并有自动化或参考真机证据；它不表示所有手机、
ROM 和 Root 管理器组合都已验证。

原生层按协议、Feature Module、UI 组件分层。Smart Hole 优先支持 DSH 核心能力和
经过选择的插件语义，不承诺无条件渲染插件市场中任意插件自带的 Web 界面。

## 手机产品的完成标准

DSH 基线之上，Smart Hole 仍要独立解决手机产品问题，例如：

- 适合单手、触屏和小屏的对话、工具调用、计划、审批与多任务交互；
- 从相册、相机、文件管理器、分享菜单和其他 App 接收上下文；
- 可靠的前后台运行、通知、进度、暂停、恢复和异常处理；
- 合理的耗电、网络、存储和移动数据控制；
- 手机上的项目、文件、终端、插件与模型管理；
- 简单安全的安装、升级、运行时维护和跨设备兼容。

这些移动端体验与可靠性，才决定 Smart Hole 最终是不是一款好用的手机 Agent。
